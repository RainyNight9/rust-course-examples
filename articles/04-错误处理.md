# 错误处理：什么时候崩，什么时候返回错误

## 导语

错误处理是《Rust 程序设计语言》第 9 章的内容，对应视频合集第 11 集（P11，约 8 分钟）。它的难点不在记住几个宏或方法，而在改变对「错误」的默认想象：Rust 没有运行时异常，失败是函数返回值的一部分，因而必须先在类型层面回答「这次失败该由谁决定」。panic 与 Result 并非两种可随意替换的写法，而是对应不可恢复与可恢复两类情形；`?` 又牵出错误类型的转换与传播。第 11 集从 00:58 的崩溃复现，经 02:36 的 Ok/Err、04:14 的问号运算符，到 05:40 的「把决定权交回去」，串起的正是这条从崩溃到返回值的判断链。

## 一、panic!：不可恢复错误的边界

panic! 表示程序遇到不该发生、也无法继续的状况，例如契约被破坏或状态不可能恢复；此时继续运行只会产生更隐蔽的错误。触发后默认沿调用栈逐层展开（unwind），调用各层析构清理数据，也可配合 `catch_unwind`；调试时设 `RUST_BACKTRACE=1` 可查看调用栈，设为 full 得到更完整信息。发布构建可在 Cargo.toml 的 `profile.release` 中设 `panic = "abort"`，跳过清理直接终止进程，配合 strip 去掉符号让二进制更小。panic 还能主动用于断言：`#[should_panic]` 把「除零必须崩」写成一条通过的测试，`expected` 只匹配崩溃信息里的一段子串。关键一条是：panic 不是错误处理，不应用它代替 Result。

## 二、Result：把失败写进类型，由 match 穷尽处理

Result 是只有 `Ok(T)` 与 `Err(E)` 两个变体的枚举，`File::open` 返回的 `Result<File, io::Error>` 是典型例子。`Result`、`Ok`、`Err` 都在预导入模块中，无需写前缀。处理它的基本方式是 match，且必须穷尽两个分支——这与第 6 章枚举的穷尽检查是同一套机制。以下片段摘自 `ch11/examples/p11_s09.rs`（运行命令 `cargo run -p ch11 --example p11_s09`）：

```rust
    let f = File::open("hello.txt");
    let f = match f {
        Ok(file) => file,
        Err(error) => panic!("打开文件失败：{error:?}"),
    };
```

只写 Ok 一支会立刻报 E0004，编译器把未覆盖的 `Err(_)` 点名出来。取值方式可按意图区分：unwrap 在 Ok 时取值、Err 时崩溃，最快但报错难定位；expect 附带自定义提示，排查更省事；unwrap_or 提供兜底值，把错误就地消化。因此「何时该 unwrap」有清晰界线：示例、原型与测试中用它让代码保持简短是合理的，库代码则几乎总应返回 Result，把重试、降级、提示的决定权留给调用方。另有一个前提常被忽略：unwrap 崩溃时要打印错误值，故要求 `E` 实现 `Debug`，自定义错误类型未派生便报 E0277。

## 三、? 运算符与错误传播

当函数不愿就地处理错误、只想交给上层，可在表达式末尾写 `?`：`Ok` 时取出值继续，`Err` 时立即从当前函数返回该错误。以下片段摘自 `ch11/examples/p11_s15.rs`（`cargo run -p ch11 --example p11_s15`）：

```rust
fn read_username_from_file() -> Result<String, io::Error> {
    let mut s = String::new();
    File::open("hello.txt")?.read_to_string(&mut s)?;
    Ok(s)
}
```

`?` 最常见的误会，是以为它会顺手把值包成 Ok。它只负责失败那条路径，成功时给的是裸值；若签名声明返回 Result，末尾却直接给出 `String`，便报 E0308，补一句 `Ok(s)` 即可。`?` 也有硬条件：只能用于返回 Result 或 Option 的函数，在返回单元类型的 main 里直接对 `File::open` 使用会报 E0277；把 main 声明为返回 `Result<(), Box<dyn Error>>` 就合法，`p11_s17.rs` 即采用此写法。

不同来源的错误能汇入同一函数，靠的是 From trait：`?` 遇到错误会尝试把它转换成函数声明的错误类型。`Box<dyn Error>` 常被称为「任意错误」的容器，标准库为它实现了大量 From 转换，适合示例与小型工具。以下片段摘自 `ch11/examples/p11_s19.rs`（`cargo run -p ch11 --example p11_s19`）：

```rust
fn open_and_check(path: &str) -> Result<(), Box<dyn Error>> {
    let _f = File::open(path)?;   // io::Error 经 From 装箱
    Ok(())
}

fn main() -> Result<(), Box<dyn Error>> {
    open_and_check("hello.txt")?;
    Ok(())
}
```

## 四、把决定权交回调用方

可恢复错误的真正含义，不是「能被自动修好」，而是「不替调用方做主」。库函数应只负责把读不到、内容为空这类情形变成 Err 返回，至于打印日志、重试还是降级，一律留给上层。以下片段摘自 `ch11/examples/p11_s21.rs`（`cargo run -p ch11 --example p11_s21`）：

```rust
pub fn read_config(path: &str) -> Result<String, io::Error> {
    let text = fs::read_to_string(path)?;
    if text.trim().is_empty() {
        return Err(io::Error::new(io::ErrorKind::InvalidData, "配置内容为空"));
    }
    Ok(text)
}
```

Rust 没有异常，错误写在函数签名里，只需查看返回类型即可判断函数会不会失败，编译器还会盯着调用方有没有处理。panic 把问题交给程序自身，Result 把决定权交回调用方，`?` 再把错误往上一层传，三者构成一条完整链条，没有隐藏控制流。判断标准可归纳为四条：示例、原型、测试可用 unwrap 或 expect；库代码优先返回 Result；契约被破坏、状态不可恢复时 panic 反而更诚实；panic 默认 unwind，发布版可设 abort。

## 常见坑

1. 用 panic! 代替 Result。panic 表示程序不该继续，而非可恢复错误的处理手段；库代码尤其不应替调用方决定终止进程。
2. match Result 只写 Ok 分支。编译器要求穷尽，漏掉 Err 报 E0004，与第 6 章枚举检查同源。
3. 误以为 ? 会自动把结果包成 Ok。它只在成功时取值、失败时提前返回 Err；函数末尾仍须写 `Ok(s)`，否则报 E0308。
4. 在返回单元类型的函数里使用 ?。报 E0277，? 只能用于返回 Result 或 Option 的函数；把 main 声明为返回 `Result<(), Box<dyn Error>>` 才合法。
5. 对自定义错误类型直接 unwrap。崩溃时要打印错误值，故要求 `E: Debug`，未派生即报 E0277。
6. 在库代码里用 unwrap 或 expect 就地消化错误，或把 `#[should_panic]` 的 `expected` 写得过于具体。前者把决定权从调用方手里拿走；后者只匹配崩溃信息中的一段子串，写得太细会让测试脆弱。

## 小结

错误是返回值而不是异常，签名写清楚，编译器替你盯着——这是第 11 集的主线。它上承第 6 章的枚举与模式匹配，下接第 10 章 trait 里负责错误转换的 From，也在后续命令行项目一集落为工程实践。建议对照视频合集按时间点回看关键镜头，再到配套代码仓库逐一运行 `ch11/examples/` 下的示例、编译 `compile-fail/` 下的反例，把 E0004、E0277 与 E0308 三类报错亲手复现一次；panic 与 Result 的取舍，往往在读过一次报错后才真正分明。
