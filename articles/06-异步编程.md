# 异步编程 —— 用少量线程撑起大量任务

## 导语

异步之难，不在于 async、await 这两个关键字，而在于它推翻了「调用函数就会执行」的默认直觉：写下 async fn 并调用它，函数体一行也不会跑。再加上标准库只定义接口、调度交给第三方运行时，初学者常把类型报错读错方向。P20 对应第 17 章「异步编程」，视频约 8.15 分钟，关键节点在 01:53 拆开 async fn 的返回类型、03:01 手写一个最小执行器、04:35 与 05:22 两处 E0277 反例。需要先说明边界：仓库 `ch20/examples/` 下只有两个纯标准库的可运行示例，并未引入 tokio 或 futures；课程里涉及 tokio、futures 的片段集中收录在 `docs/snippets/p20.md`，按视频顺序保留原样，属于教学摘录而非可独立编译的程序，复现它们须自行在 Cargo.toml 添加依赖。

## 一、先厘清并发与并行

线程适合 CPU 密集任务，但一个连接开一个线程代价太高。异步用状态机把大量处于等待中的任务挂在少量线程上，尤其适合 I/O 密集的服务。要区分两个词：并行是同一时刻真的在多核上同时运行；并发是多个任务在重叠的时间段里交替推进。异步属于后者，遇到 I/O 等待就让出执行权，让同一个线程去推进别的任务。

标准库只定义 Future 接口，具体调度由 tokio、async-std 这类运行时提供。因此动手前要配好依赖：课程示例用 tokio 1 并开启 macros、rt-multi-thread，配合 futures 0.3，edition 为 2024。依赖未配好便去读类型报错，往往徒劳无益。

## 二、async fn 造出的是惰性状态机

Future 表示一个「还没完成的值」，核心是 poll，返回值可能是 Poll::Pending（尚未就绪）或 Poll::Ready(T)（完成）。写 async fn 时函数体不会立刻执行，而是返回一个实现了 Future 的匿名状态机；等价写法是 `fn -> impl Future<Output = u32>`（`p20_s07.rs`）：

```rust
// 下面两种写法等价
async fn answer() -> u32 { 42 }

fn answer_explicit() -> impl std::future::Future<Output = u32> {
    async { 42 }
}
```
（出自 `ch20/examples/p20_s07.rs`，运行 `cargo run -p ch20 --example p20_s07`）

惰性几乎是所有异步困惑的源头：构造 future 只是打包状态与参数，不做实际工作；只有执行器反复 poll，或被 .await 挂到运行时上，代码才往前走一步。在 .await 处，当前任务让出执行权，运行时在数据就绪时再回来 poll 它。所以 await 只是挂起点，真正驱动它的是运行时。`#[tokio::main]` 把 async main 包成同步入口，背后建好运行时再 block_on；它不是可有可无的语法糖，而是决定了由谁驱动。在函数体里放入 println! 却不 .await，就会误以为输出丢失。

## 三、执行器负责推进：从最小 block_on 到运行时

若要验证「得有人推进」，可以手写一个不依赖第三方 crate 的执行器（`p20_s11.rs`）：用 `std::task::Wake` 造一个空 Waker，把 future 用 Box::pin 钉在堆上，循环 poll，遇到 Pending 就让出时间片。

```rust
fn block_on<F: Future>(fut: F) -> F::Output {
    let waker = Waker::from(Arc::new(Noop));
    let mut cx = Context::from_waker(&waker);
    let mut fut = Box::pin(fut);
    loop {
        match fut.as_mut().poll(&mut cx) {
            Poll::Ready(v) => return v,
            Poll::Pending => std::thread::yield_now(),
        }
    }
}
```
（出自 `ch20/examples/p20_s11.rs`，运行 `cargo run -p ch20 --example p20_s11`）

这段循环清楚地说明「标准库只给接口、不管调度」：poll、Pin、Waker 是执行器的实现细节，写业务代码时很少直接碰。它也解释了 !Unpin：async 状态机可能跨 await 存指向自身的引用，移动即失效，因此 poll 要求 `Pin<&mut Self>`；对 !Unpin 的 future 直接用 Pin::new 会以 E0277 失败，改用 Box::pin 钉到堆上（`p20_s17.rs`）。可归纳为三句话的心智模型：async 造状态机，await 是让出点，运行时负责推进。

## 四、把多个 future 组织起来：并发、取消与任务边界

连续写两个 .await 是串行执行，第二个要等第一个完成；想让它们同时推进，用 join! 或 tokio::join! 把多个 future 组合成一个。几个宏分工要明确：join! 等全部完成并按位置返回结果，try_join! 针对返回 Result 的 future、任一出错就提前返回，select! 是谁先完成用谁、其余分支立刻取消。

并发不等于每个 future 都会跑完。timeout 或 select! 分出胜负后，落选分支会在 .await 处被 drop，做了一半的写入就此作废，这就是取消安全；不可默认它总会执行到底，把不可重入的状态留在半路。任务数量在运行时才知道时，可用 join_all 收集全部 future 一起等待；想哪个先完成就先处理哪个，用 FuturesUnordered 配合 while let 逐个取结果；要限流则用 buffer_unordered(n)，最多 n 个在跑，完成一个再补一个。Future 给一个值，Stream 给一串值，相当于异步版本的迭代器，配合 StreamExt 的 next、map、filter 可写成熟悉的流水线。

还要分清三层：最底层是 OS 线程，运行时在其上调度任务，每个任务里又可以有多个 future。tokio::spawn 要求 future 满足 Send + 'static，借用栈上变量会被拒，得先 Arc::clone；CPU 密集的计算会占住所在线程、让同线程上的其它任务得不到推进，应交给 spawn_blocking 线程池，不宜放进 async 函数。

## 五、Send 约束与跨 await 的锁

P19 的 spawn Send 约束，在异步里以另一种形式重现。`std::sync::MutexGuard` 是 !Send，只要它活过 .await，整个 async 块就不满足 Send，tokio::spawn 会以 E0277 拒绝（`p20_s20.rs`，「守护让 future 不 Send」）。修法是让守护在 await 前离开作用域，临界区只做数据操作、尽快放掉守护。这与同步篇「锁不能跨 await」是同一条原则，也再次说明 Send、Sync 是 unsafe 自动派生的标记 trait，由编译器按字段推导。

## 常见坑

1. 把 `#[tokio::main]` 当成可有可无的语法糖。它把 async main 包成同步入口、建好运行时再 block_on；缺了它，async fn 没有执行器可依托。
2. 把 async fn 的返回值当普通结果用，或在函数体里放 println! 却不 .await，误以为函数体已经执行。
3. 默认每个 future 都会跑到底。select! 与 timeout 分出胜负后，落选分支在 .await 处被 drop，做了一半的写入作废，这就是取消安全。
4. 连续两个 .await 误以为在并发，实际串行；另外 join_all 一次放开全部任务容易压垮下游，应用 buffer_unordered(n) 限流。
5. 把 `std::sync::MutexGuard` 持有过 .await。守护是 !Send，整个 future 随之不 Send，tokio::spawn 报 E0277；应让守护在 await 前离开作用域。
6. 把 CPU 密集计算放进 async 函数、占住所在线程；或对 !Unpin 的 future 直接用 Pin::new，应改 Box::pin。

## 小结

从 async fn 返回惰性 Future，到手写 block_on 证明「不推进就一步不走」，再到 join!、取消安全与 tokio::spawn 的 Send 约束，P20 的主线只有一句：async 造状态机，await 是让出点，运行时负责推进。建议把 `p20_s07.rs` 与 `p20_s11.rs` 亲手运行一遍，再对照两处 E0277 反例理解 Pin 与锁跨 await 的边界。完整讲解见 B 站《Rust 程序设计语言》22 集视频合集的 P20，两个纯标准库可运行示例、故意报错反例以及 tokio / futures 教学摘录都在配套代码仓库 rust-course-examples 中；摘录片段需按上表自行补齐依赖后才能编译，仓库里并不提供可直接运行的 tokio 示例。
