# 无畏并发 —— 所有权规则延伸到多线程

## 导语

并发之所以难，不在于创建线程，而在于数据竞争：多个指针同时访问同一份数据、至少有一方写入、彼此没有同步，三者凑齐就可能出现只在特定时序下才复现的错误。传统语言把这份风险留到运行时或代码评审，Rust 则把所有权与借用规则从单线程延伸到多线程，让「多个可写引用同时存在」在编译期就无法通过。对应课程 P19（第 16 章「无畏并发」，全片约 8 分钟），关键节点包括 01:07 复现 Rc 跨线程报错、04:26 演示 `Arc<Mutex<T>>`、05:47 比较 AtomicUsize。理解这条主线比记住几个 API 更重要：Rust 并不承诺让并发变简单，它承诺让并发错误在编译时暴露出来。

## 一、编译期先划红线：Send、Sync 与 move 闭包

数据竞争的三个条件里，Rust 用所有权与借用规则掐掉了「多个可写引用同时存在」，再用两个标记 trait 补齐跨线程的可信边界。Send 表示值的所有权可以安全转移到另一线程，Sync 表示值的引用可以被多个线程安全共享，后者等价于「`&T` 能 Send」。它们是无方法的标记 trait，由编译器按字段自动派生，字段全部满足才成立；手写实现要写 unsafe impl，等于向编译器作出担保，不能当成普通接口随手实现。

把边界落到签名上，`std::thread::spawn` 要求闭包满足 `FnOnce() -> T + Send + 'static`，返回值同样要 Send 与 'static。'static 常被误读为「数据要活到程序结束」，实际约束的是捕获方式：闭包必须拥有用到的值，不能持有指向当前栈帧的临时引用。配合 move 关键字，闭包把变量的所有权搬进去，原位置此后不可再碰；i32、`&T` 这类 Copy 类型只是按位复制，堆上的 String 则是真移动。加了 move 也不代表一定安全，闭包整体仍得满足 Send。仓库里的反例 `p19_s04.rs` 把 `Rc<i32>` 用 move 搬进 spawn，因 Rc 的引用计数不是原子操作、被判为 !Send，编译器以 E0277 直接拒绝。换成 Arc 即可，若还要改里面的值，再套一层 Mutex。

## 二、第一种写法：用消息传递转移所有权

避开共享最彻底的办法，是让数据只属于一个线程。`thread::spawn` 接收闭包，在新线程执行；闭包要用到主线程的变量，通常加 move 把所有权搬入（`p19_s08.rs`）。spawn 返回 JoinHandle，join 会阻塞到线程结束并返回 Result，线程 panic 时拿到 Err；不 join 的话，主线程结束时新线程可能被直接掐断。

若只想借用外层栈上数据，`std::thread::scope` 更省：编译器保证作用域返回前所有线程都结束，因此无需 'static、也无需 clone（`p19_s09.rs`），代价是它会阻塞到全部线程收尾。

跨线程传值则用 `std::sync::mpsc`，即多生产者单消费者通道。tx 负责发、rx 负责收，用 move 把 tx 搬进新线程后，值的所有权就从发送方转移到接收方，不需要共享内存（`p19_s12.rs`）：

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();
    thread::spawn(move || {
        tx.send(String::from("hi")).unwrap();
    });
    let msg = rx.recv().unwrap();   // 阻塞等待
    println!("收到 {msg}");
}
```
（出自 `ch19/examples/p19_s12.rs`，运行 `cargo run -p ch19 --example p19_s12`）

通道允许多个生产者，把 tx 克隆几份分给不同线程即可；遍历 rx 时，所有发送端都被丢弃、通道关闭，迭代自然结束，不必手动发结束信号。带容量的 sync_channel 格位固定，队列满时 send 阻塞形成背压，避免撑爆内存；接收端被丢弃时 send 返回 SendError，try_send 与 recv_timeout 可无阻塞探状态。

## 三、第二种写法：用共享状态与锁排定顺序

当多个线程确实要改同一份数据，就用 Mutex 保证同一时刻只有一个线程拿到锁，再用 Arc 让多个线程共享这个 Mutex 的所有权。Rc 不能跨线程，正因为它的计数不是原子的，而 Arc 的计数是原子操作（`p19_s16.rs`）：

```rust
let counter = Arc::new(Mutex::new(0));
let mut handles = vec![];
for _ in 0..10 {
    let c = Arc::clone(&counter);
    handles.push(thread::spawn(move || {
        *c.lock().unwrap() += 1;
    }));
}
for h in handles { h.join().unwrap(); }
println!("结果：{}", *counter.lock().unwrap());
```
（出自 `ch19/examples/p19_s16.rs`，运行 `cargo run -p ch19 --example p19_s16`）

持锁期间 panic 是另一处需要正视的情形：数据可能改到一半，Rust 把锁标记为「中毒」，再次 lock 会拿到 Err。到处写 `lock().unwrap()` 会把 panic 传播开、拖垮服务，稳妥做法是显式匹配错误，用 into_inner 取回被保护的数据再定夺（`p19_s17.rs`）。锁还有两个高频事故：以不同顺序锁两把 Mutex，两个线程各持一把互等即死锁；把 MutexGuard 攥到跨 .await 或做耗时 I/O，锁被长期占住。原则是临界区只放必要的数据操作，取出值就 drop 守护，耗时逻辑挪到锁外；try_lock 拿不到立刻返回，也便于打破死锁。

## 四、更轻的一档：原子类型与两条路的收束

只累加一个计数就动用 Mutex 偏重。AtomicUsize 的 fetch_add 是一条原子指令，不加锁也不进内核；示例 `p19_s21.rs` 里 `Ordering::Relaxed` 已足够，只保证加法不丢。它不提供同步其它数据的内存序，若要用计数结果去发布别的状态，得换更强的 Ordering。

消息传递避免共享，共享状态靠锁同步，两条路看似不同，落脚点一致：channel 靠转移所有权避免共享，Mutex 靠加锁排定顺序，背后都由所有权加 Send、Sync 兜底。进入 P20 异步篇后，spawn 的 Send 约束、锁不能跨 await 会原样再出现，可对照着看。

## 常见坑

1. 把 'static 理解成「数据必须活到程序结束」，于是到处套 Arc。它约束的是闭包必须拥有捕获值、不能借栈上临时引用，与全局存活无关。
2. 多个生产者时忘了释放主线程自己那份 tx（`p19_s14.rs`）。接收端用 for 遍历会一直等到通道关闭，只要还有一个发送端活着就永不结束；调试可改用 recv_timeout 加超时。
3. 到处写 `lock().unwrap()`。持锁线程 panic 会让锁中毒，unwrap 把 panic 继续传播；应显式匹配 PoisonError，用 into_inner 取回数据。
4. 以不同顺序锁两把 Mutex 造成死锁，或把 MutexGuard 攥到跨 .await、做耗时 I/O，让锁被长期占住。
5. 用 `Ordering::Relaxed` 去同步别的数据。它只保证计数加法不丢失，不承担跨线程的内存可见性排序。
6. 把 Send、Sync 当成需要手写实现的普通 trait。它们是无方法的 unsafe 标记 trait，由编译器按字段自动派生，手写要 unsafe impl。

## 小结

从 Rc 被 E0277 拦下，到 channel 转移所有权、`Arc<Mutex<T>>` 排定顺序，再到 AtomicUsize 的轻量一档，P19 反复验证的是同一件事：所有权规则延伸到多线程后，数据竞争在编译期就无处藏身。建议把例题亲手敲一遍，尤其试一次删掉 drop(tx)、以及把中毒分支改成 unwrap 的差别。完整讲解见 B 站《Rust 程序设计语言》22 集视频合集的 P19，全部可运行示例与故意报错反例都在配套代码仓库 rust-course-examples 中，按上表命令即可逐一复现。异步篇会接着讨论 Send 约束在 Future 上如何再次出现。
